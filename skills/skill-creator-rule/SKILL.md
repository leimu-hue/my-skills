# 编写 SKILL 规约

## 1. 约束类型

SKILL 中只能包含 Agent 执行约束，禁止包含开发者维护性约束。

**允许**：Agent 在运行时如何执行动作的约束（如：搜索时必须先调用 xxx API、处理失败时必须重试 N 次）。

**禁止**：面向开发者的人工维护约束（如：修改此文件后需手动更新 xxx 配置、部署前需运行 yyy 脚本）。

## 2. 约束变更流程

新增、删除或修改约束时，必须先阅读全文，确认：
- 无重复约束（同一规则不得以不同措辞出现多次）
- 无矛盾约束（新约束不得与已有约束冲突）

若发现重复或矛盾，应合并或删除冗余项后再写入。

## 3. Description 编写

description 必须同时说明：
- **做什么**：技能的核心功能
- **何时触发**：具体的用户意图/上下文

所有"何时触发"信息放在 description 中，不要放在正文里。描述应略带"推力"以避免漏触发。

## 4. 正文长度

SKILL.md 正文控制在 500 行以内。超出时应：
- 拆分到 references/ 目录下的独立文件
- 在正文中添加清晰的指引，说明何时读取哪个参考文件

## 5. 写作风格

- 优先使用祈使句
- 解释"为什么"比强制"MUST"更有效
- 保持泛化，避免过度特化到特定示例
- 使用"理论心智"——假设模型能理解意图

## 6. 参考文件引用

从 SKILL.md 引用参考文件时，必须说明：
- 文件内容是什么
- 何时应该读取该文件

当参考文件超过 300 行时，应在文件开头添加目录。

## 7. 多领域组织

当技能支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md (工作流 + 选择逻辑)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
模型只读取相关的参考文件。

## 8. 测试用例

技能应包含测试用例（存放在 `evals/evals.json`）：
- 2-3 个真实用户可能说的测试提示词
- 包含预期输出描述
- 可验证输出的技能应设置断言

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示",
      "expected_output": "预期结果描述",
      "files": []
    }
  ]
}
```
