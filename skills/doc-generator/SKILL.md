# 项目文档生成器

根据项目代码生成标准文档，输出到 `docs/<需求名称>/`。

## 文档范围

文档分为**核心文档**与**扩展文档**两级。用户可指定需要的文档，未指定时默认生成核心三件套。

### 核心文档（默认生成）

| 序号 | 文档 | 内容要点 | 模板参考 |
|------|------|----------|----------|
| 01 | 需求规格.md | 功能概述、功能需求清单、业务规则需求、非功能需求 | [模板](./references/templates/01-需求规格.md) |
| 02 | 概要设计.md | 系统架构、模块划分、类图关系、核心流程概要、依赖关系 | [模板](./references/templates/02-概要设计.md) |
| 03 | 详细设计.md | 每个方法的算法流程、分支逻辑、关键实现细节 | [模板](./references/templates/03-详细设计.md) |

### 扩展文档（按需生成）

| 序号 | 文档 | 适用条件 | 模板参考 |
|------|------|----------|----------|
| 04 | 数据库设计.md | 需求涉及新增表/字段变更，或用户明确要求 | [模板](./references/templates/04-数据库设计.md) |
| 05 | API文档.md | 需求涉及新增/修改接口，或用户明确要求 | [模板](./references/templates/05-API文档.md) |
| 06 | 测试计划.md | 用户要求交付测试用例，或项目有测试规范要求 | [模板](./references/templates/06-测试计划.md) |


### 范围确定规则

1. 用户明确指定文档类型 → 按指定生成
2. 用户说"完整文档""交付文档""全套文档" → 生成全部 6 份（01-06）
3. 用户说"生成文档"未指定 → 默认核心三件套，并在生成后**主动询问**是否需要补充扩展文档

## 适用与边界

### 适用场景
- 新项目快速生成标准文档
- 老项目补齐历史文档
- 交付前统一文档格式与版本信息

### 非适用场景
- 用户只要求修改单篇已有文档
- 项目代码或目录不可访问
- 用户明确要求输出格式与本 Skill 模板冲突（需先确认）

## 输入要求

- 目标项目目录（必需）
- 需求名称（必需，用于目录名）
- 项目名称（建议，缺省可由目录名推断）
- 文档范围（可选，默认核心三件套；可指定"完整"或具体文档名）
- 输出语言（默认中文）
- 是否读取 Git 信息（默认开启）

## 执行原则

- 仅基于可见代码与仓库信息生成内容，不臆造不存在的模块、表、接口。
- 若信息不足，在文档中显式标注"待确认/待补充"。
- 目录已存在时，先读取已有文档并在不破坏原结构前提下增量补全。
- 默认生成 Markdown 文件，不额外生成二进制格式。
- **扩展文档仅在代码中有对应内容或用户明确要求时才生成**，不无中生有。
- **文档修正必须原地替换**：用户指出文档中的错误结论或数据时，直接修改对应位置的内容为正确值。**严禁**在文件末尾追加"纠正说明""勘误""更正记录"等补丁段落——这会让同一文档同时存在错误和正确内容，造成歧义。正确做法：定位错误段落 → 替换为正确内容，文档其余部分保持不变。

## 工作流程

### 1. 确定文档范围
- 从用户输入中解析文档范围
- 未指定 → 默认核心三件套（01/02/03）
- 用户说"完整"/"交付"/"全套" → 全部 6 份（01-06）
- 用户列明具体文档 → 按清单生成
- 若不确定是否需要扩展文档 → 先分析代码，再向用户建议

### 2. 理解项目代码
- 分析项目目录结构
- 优先读取入口层、应用层、领域层、基础设施层核心文件
- 识别领域模型、数据仓储、业务流程与外部依赖
- 提炼模块边界与关键数据流
- **根据代码实际情况，判断哪些扩展文档有必要生成**

### 3. 版本信息获取
- 检查是否为 Git 仓库
- 提取提交次数与最近提交记录（若可用）
- 按版本号规则生成版本号

### 4. 作者信息获取
按以下三级优先级获取作者：

| 优先级 | 来源 | 获取方式 |
|--------|------|----------|
| 1 | 当前用户 | PowerShell: `$env:USERNAME`，Linux/macOS: `whoami` |
| 2 | Git 提交作者 | `git log -1 --format=%an` |
| 3 | 置空 | 若以上均无法获取，作者字段留空（`作者：` / `Author: `） |

### 5. 创建文档目录
在项目根目录下创建 `docs/<需求名称>/`。

目录已存在时 → 检阅现有文档作为参考 → 增量更新而非覆盖。

### 6. 生成文档

按已确定的文档范围，参考对应模板逐份生成。

- 模板链接见上方"文档范围"表格
- 生成顺序按序号从小到大
- 核心文档（01-03）必生成；扩展文档（04-06）仅在范围内时生成

### 7. 版本管理

#### 版本号规则
- **有 Git 版本控制**：`1.{yy}.{Mdd}.{git提交次数}`
- **无 Git 版本控制**：`1.{yy}.{Mdd}.{hmm}`

字段约定：
| 字段 | 含义 | 示例 |
|------|------|------|
| `{yy}` | 年份后两位 | `26`（2026年） |
| `{Mdd}` | 月份不补零 + 日期补零 | `509`（5月9日） |
| `{git提交次数}` | `git rev-list --count HEAD` | `1234` |
| `{hmm}` | 小时不补零 + 分钟补零 | `1530`（15:30） |

#### Git 提交记录提取
- `git rev-list --count HEAD` → 总提交次数
- `git log --pretty=format:"%h - %s (%an, %ar)" --date=short` → 最近提交记录
- 提交记录用于生成变更日志和版本历史；无法获取时使用"初始版本"占位

#### 变更日志格式
每个文档头部包含变更日志：

```markdown
## 变更日志

| 版本 | 日期 | 作者 | 变更内容 |
|------|------|------|----------|
| <动态生成> | <当前日期> | <动态获取> | 初始版本 |
```

### 8. 文档头部信息

每个文档必须包含：

```markdown
# 文档标题

**项目名称**：XXX项目
**作者**：<动态获取>
**日期**：<当前日期>
**版本**：<动态生成>

## 变更日志
...
```

> 作者字段通过第4步三级优先级动态获取，不硬编码固定作者名。

### 9. 内容质量规则

**文档内容边界（严格遵守）：**

| 文档 | 阅读对象 | 内容边界 | 核心价值 |
|------|----------|----------|----------|
| 01-需求规格 | 产品经理、评审人员 | 业务需求、功能清单、非功能需求，禁止出现技术实现细节 | 让非技术人员理解"要做什么" |
| 02-概要设计 | 评审人员、架构师、项目经理 | 高层设计（架构、模块、流程、依赖），**禁止**出现代码片段、伪代码、变量名、方法签名 | 让评审人员理解"系统怎么设计" |
| 03-详细设计 | 开发人员、代码审查者 | 必须包含代码级实现细节：方法签名、算法伪代码、分支逻辑、异常处理、**代码变更清单** | 指导开发实现，是编码的直接依据 |

**核心文档：**
- 需求规格中的功能点需与代码中的模块/接口可追溯
- 概要设计需体现模块职责与依赖方向，避免仅罗列文件名
- 详细设计需覆盖关键方法的输入、处理、输出与异常路径，**必须包含代码变更说明章节**

**扩展文档（仅在生成时适用）：**
- 数据库设计需区分"已存在表结构"和"建议优化项"
- API 文档需标注鉴权、请求参数、响应示例与错误码
- 测试计划需至少包含正常、边界、异常三类用例
- 部署与用户手册需区分"部署步骤"和"操作说明"

### 10. 输出收尾

- 返回生成结果摘要：输出目录、文件清单、版本号来源（Git/时间）
- 对缺失信息给出待确认项列表，便于下一轮补全
- **若仅生成了核心文档，主动询问用户是否需要补充扩展文档**

### 11. 生成总结文档（已移除）

> 总结文档（08）已根据需求移除，不再生成。

## 常见错误

| 错误 | 正确做法 |
|------|----------|
| 不管需求范围，强制生成全部 6 份文档 | 先确定文档范围，默认仅生成核心三件套 |
| 臆造不存在的模块/表/接口填入文档 | 仅基于实际代码生成，缺失处标注"待确认" |
| 目录已存在时直接覆盖 | 先读取已有文档，增量补全不破坏原结构 |
| 代码中无数据库/接口却生成了对应文档 | 扩展文档仅在代码有对应内容或用户明确要求时才生成 |
| 模板版本号写死 `V1.0` | 必须按版本号规则动态生成（Git提交次数或时间戳） |
| 概要设计仅罗列文件名无模块职责 | 须体现模块职责、依赖方向、核心流程 |
| 概要设计包含代码片段或伪代码 | 概要设计面向评审人员，禁止出现代码实现细节 |
| 详细设计缺少代码变更说明 | 必须包含代码变更清单（文件、方法签名、数据库变更） |
| API 文档缺少鉴权/错误码说明 | 每个接口须标注鉴权方式、请求参数、响应示例、错误码 |
| 测试计划仅写正向用例 | 至少包含正常、边界、异常三类用例 |
| 作者字段硬编码 | 按三级优先级动态获取（用户 > Git作者 > 置空） |
| 跳过 Git 信息提取直接手工填版本 | 先用 `git rev-list --count HEAD` 获取真实提交次数 |
| 变更日志不更新仅保留初始版本 | 每次生成时追加新版本行，保留历史记录 |
| 生成完核心文档后未询问是否需要扩展文档 | 输出收尾时主动询问用户 |
| 数据模型/API 清单无中生有 | 代码中无对应内容时标注"本次需求无新增或变更数据模型/API" |
| 实现指引仅列文件名无任务说明 | 每个任务须含目标、涉及文件、关键注意点，Agent 可直接按顺序执行 |
| 用户纠正错误时在文件末尾追加纠正说明 | **原地替换错误内容**为正确值，不新增任何补丁段落；文档只保留正确版本 |
